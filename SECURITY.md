# Security

AWS hackathon-final pass, phase 9. This consolidates the security posture
already documented piecemeal across `AWS_ARCHITECTURE.md`'s "Security
architecture summary", `JUDGING_EVIDENCE.md`'s fixed-vulnerability
history, and `FINAL_PRODUCTION_READINESS_REPORT.md`'s dependency-scan
results, into one place. See `THREAT_MODEL.md` for the trust-boundary
analysis this posture is meant to address, and `docs/observability-runbook.md`
for detection/alerting on the controls below.

## Authentication and authorization

- Every mutating REST endpoint and the WebSocket route require
  `X-Demo-Access-Token` (a master token or a live paired-device token —
  see `backend/app/api/deps.py`'s `require_demo_access_token`/
  `credential_is_valid`).
- Minting new pairing codes and administrative device revocation
  additionally require the master token specifically
  (`require_master_demo_access_token`) — a compromised device token
  cannot escalate to pairing arbitrary new devices.
- Token comparison is constant-time (no early-exit string comparison
  that would leak length/prefix information via timing).
- **Fail-closed by construction**: if no master token is configured at
  all when `ENVIRONMENT=production`, mutating endpoints return 503,
  never silently open (`validate_production_configuration`, checked at
  process startup, not per-request).
- Pairing-code-to-device-token exchange is atomic (phase 3): one
  DynamoDB `TransactWriteItems` call combines code consumption, token
  creation, and the device-id index write — a code is never burned on a
  partial failure, and a bounded retry budget
  (`DEVICE_EXCHANGE_MAX_ATTEMPTS`) prevents an unbounded collision-retry
  loop from becoming its own DoS vector.

## Transport

- HTTPS/WSS end-to-end when `CertificateArn` is supplied — this
  template's *required* default. A deploy-time CloudFormation Rule
  refuses to deploy either ECS service without either a certificate or
  an explicit, visible `AllowInsecureDemoHttp=true` opt-in for
  local/demo-only testing.
- The Fire TV client independently refuses to open a plaintext
  connection in a release build regardless of what the backend allows
  (`assertSecureTransportForRelease` — defense in depth, not reliance on
  server-side configuration alone).

## Rate limiting and abuse resistance

- Layered WAF rules: a tight limit scoped to `/v1/auth/*`
  (pairing-code/pair/revoke), a looser site-wide limit underneath.
- Application-layer `PairingRateLimiter` as a second line of defense
  behind the WAF (distributed, DynamoDB-backed, so it holds across
  multiple ECS tasks — see `BackendDesiredCountRequiresCrossInstanceBroker`'s
  own reasoning for why a naive in-process limiter would not).
- Two CloudWatch alarms (`<stack>-pairing-failures`,
  `<stack>-pairing-throttling`) and a third
  (`<stack>-authentication-failures`) watch for the traffic signature of
  brute-forcing a pairing code or the demo token.

## Secrets

- Never committed to the template, a CloudFormation parameter, git, or a
  log line.
- Generated by Secrets Manager, read at ECS task-start via the
  `Secrets:` mechanism (resolved by the platform, never passed as a
  plain environment variable) or via a Lambda's own
  `secretsmanager:GetSecretValue` IAM permission scoped to the exact
  secret ARN — never a wildcard `secretsmanager:*`.
- `docs/deployment-runbook.md`'s "Secret rotation" section documents the
  procedure, including the one known asymmetry (the legacy Alexa Skill
  Lambda resolves its copy of the token once, at stack-deploy time, via
  a CloudFormation dynamic reference, so rotating the underlying secret
  requires a stack re-deploy for that one Lambda specifically to pick up
  the new value — documented, not silently wrong).

## Encryption and data protection

- DynamoDB table encrypted at rest with a customer-managed KMS key
  (`RaceStateTableKey`), not the AWS-owned default key — gives this
  stack its own auditable key policy and independent rotation.
- Secrets Manager encrypts secrets by default.
- DynamoDB point-in-time recovery enabled; `Retain` deletion policy on
  the table and its KMS key, so a stack deletion cannot silently destroy
  race data or make encrypted data unrecoverable.

## Audit logging

- Every auth failure, pairing event, and device revocation is logged as
  one structured JSON line via `audit_log` (`backend/app/observability.py`).
- A hard guard (`AuditFieldViolation`) refuses to log any field whose
  name ends in `token`, `secret`, `password`, `key`, or similar —
  enforced by **raising before the log call happens**, not by
  best-effort redaction after the fact. A test in
  `backend/tests/test_observability.py` fails CI if this guard is ever
  weakened.
- `correlation_id` is sanitized against a strict charset before being
  echoed back or logged (closes a header-injection vector — see
  `JUDGING_EVIDENCE.md` §4 for the specific fix history).

## Least-privilege IAM

- `BackendTaskRole`/`McpTaskRole`/each Lambda's execution role scope
  `secretsmanager:GetSecretValue` to the one secret ARN they actually
  need.
- `McpServerService` has no DynamoDB permissions at all — it only ever
  calls the backend's own authenticated REST API, never touches the
  table directly.
- Bedrock's `bedrock:InvokeModel` grant is scoped to exactly the
  configured model ARN (`BedrockModelArn`), never `bedrock:*` — enforced
  by both the IAM policy and `infrastructure/tests/test_template_security.py`'s
  `TestBedrockWiring` class.
- X-Ray/OTel-collector write actions (`xray:PutTraceSegments`,
  `xray:PutTelemetryRecords`) do not support resource-level scoping in
  IAM, so they're granted as `Resource: "*"` — the narrowest AWS
  actually allows for this action, not a broader grant of convenience.

## Container hardening

- The backend's ECS task definition runs with `ReadonlyRootFilesystem:
  true` and `Capabilities: {Drop: [ALL]}` — the backend never writes to
  its own container filesystem at runtime (all durable state is
  DynamoDB), so the root filesystem is read-only with only a small `/tmp`
  scratch volume mounted.
- The deployment circuit breaker (`DeploymentCircuitBreaker: {Enable:
  true, Rollback: true}`) automatically rolls back a deployment that
  cannot reach a steady state, rather than leaving a broken task
  definition "successfully deployed" while serving 5xx to real traffic.

## Dependency and static-analysis scanning

- `npm audit` (Fire TV) is gated by an honest exception policy
  (`scripts/npm_audit_gate.py` + `fire-tv/security/npm-audit-policy.json`)
  — a vulnerability is only allowed through if it has a current,
  unexpired, named-owner exception on file, never silently ignored; see
  `scripts/preflight.sh`'s own run of this gate for current status.
  — third-party vendor images (the X-Ray daemon, the ADOT collector
  sidecar) are pinnable to an immutable digest via
  `XRayDaemonImage`/`OTelCollectorImage` parameters, though this
  sandbox's lack of container-registry access means the digest itself
  could not be resolved here (see those parameters' own descriptions;
  tracked in `EXTERNAL_RELEASE_CHECKLIST.md`).

## Reporting a vulnerability

This is a hackathon submission, not a maintained production service with
a standing security contact. If you find a genuine vulnerability in this
codebase, please open an issue in the repository it was submitted from
rather than disclosing it publicly, and describe the concrete impact —
consistent with this document's own "do not hide, ignore, or
misrepresent vulnerabilities" principle, which applies to anyone
reviewing this code as much as to the pass that produced it.

## What's real vs. externally verified

Every control above is implemented and locally testable (see
`infrastructure/tests/test_template_security.py`,
`backend/tests/test_observability.py`, and `scripts/preflight.sh`'s
green run). **None of it has been verified against a real AWS
deployment** — this environment has no AWS credentials. See
`FINAL_PRODUCTION_READINESS_REPORT.md` for the explicit source-readiness
vs. externally-verified-deployment-readiness distinction.
